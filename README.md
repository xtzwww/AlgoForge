# 基于智能体的编程课程学习过程分析与反馈系统

**面向编程类课程的教学辅助系统 —— 过程可溯、学情可见、反馈分层**
*An Intelligent-Agent-Based Learning-Process Analysis and Feedback System for Programming Courses.*

## 一、项目定位

### 要解决的问题

线上编程教学普及后，暴露出两个痛点：

1. **学情不可见** —— 教师只看到最终提交结果，看不到学生「怎么学、卡在哪」；
   现有平台的学情分析多停留在登录时长、视频观看等浅层行为指标。
2. **反馈无效** —— 传统 OJ 只给 AC / WA 判定，不给「为什么错、怎么想」；
   学生拿到 WA 之后纠错成本全压在自己身上，且同样的错误会反复犯。

本系统同时应对这两点：**让学习过程可观测，让反馈可分层、可追溯。**

### 核心思路（升级后的主线）

> **以「反馈」组织整个系统**，而不是把功能平铺成「学生端 + 教师端 + 检测」三块。

```
                    学习过程数据
        （提交结果 + 编辑行为轨迹 + 历史记录）
                          │
          ┌───────────────┴───────────────┐
          ▼                               ▼
    给学生 · 学反馈                  给教师 · 教反馈
  分层释放的错因引导              班级知识点掌握度
  「这题你卡在哪」                「全班弱在哪」
  「这个错误你犯过 N 次」         「下节课该讲什么」
          │                               │
          └───────────────┬───────────────┘
                          ▼
                AI 使用检测（信号维度）
       学生端 =「学习过程提示」，教师端 =「过程特征标记」
```

**AI 检测为什么是「一个维度」而不是「一个模块」**：
检测的目的不是抓学生，而是**给学生一个关于自己学习方式的反馈**。
它融入上面两条链路，因此不需要独立的检测服务，也不以「检测准确率」为目标。

### 差异化：过程数据是别人拿不到的

本系统自带 Monaco 编辑器，因此可以采集**编辑过程**：
什么时候粘贴的、粘贴后改了多少、编辑节奏如何、有没有反复调试。

| | 通用检测工具（GPTZero / Turnitin） | 本系统 |
|---|---|---|
| 能看到什么 | 只看最终文本 | **文本 + 写作过程** |
| 判据 | 统计特征（困惑度、突发性） | **行为轨迹（客观可复现、可向学生解释）** |
| 适用场景 | 自然语言 | **编程作业（代码）** |

> **粘贴 80 行后零修改直接提交**（代写）与**粘贴后大量改写、反复试错**（参考题解），
> 在纯文本上看起来一样，在过程数据上完全不同。
> 这个区分度是**自有编辑器才具备的数据优势**，也是本设计的创新点所在。

## 二、系统功能

### 2.1 学生端 · 学反馈

**分层释放的错因引导（核心功能）**

现有实现把 AI 诊断的三段内容一次性倾泻给学生（`【错在哪】【提示】【怎么改】`），
学生往往直接看「怎么改」，跳过思考环节。本系统改为**分层释放**：

```
提交（WA）
   ↓
【第一层】错在哪          指出实际错因，用学生能读的中文说明
   ↓  点「还是不会，给点提示」
【第二层】提示            给方向，仍不给答案
   ↓  点「还是不会，直接看怎么改」
【第三层】怎么改          完整的修改建议
   ↓  点「重新自己想」
（收起，回到只看第一层）
```

**教学设计依据**：支架式教学（scaffolding）——逐步撤除支持，
让学生尽可能自主完成。这是教育学理论在系统里的具体落地。

**三个实现上的取舍**（都是刻意的）：

- **初始什么都不显示**，连「错在哪」也在按钮后面。若默认展开第一层，
  「还是不会」就退化成「显示剩余内容」，对思考的推动弱得多。
- **释放层数按实际内容算**，不是固定三层。模型跳过某一节时按钮直接跳到下一节，
  不会点开一个空面板 —— 打开门看见空房间会被读成 bug。
- **释放进度不持久化**，离开页面再回来重新从第一层开始。门槛是一次自我评估，
  隔天回来看同一道题的是另一个学习者；存下「已看过答案」等于让这次回访失去意义。

**其余学生端能力**

| 能力 | 说明 |
|---|---|
| 在线编程与提交 | Monaco 编辑器（自定义主题、多语言切换）+ 一键编译运行 |
| 多语言判题 | C++ / Python / Java，判定 AC / WA / TLE / MLE / CE / RE |
| 错题本 | 自动归档、分析状态可见、失败可重试 |
| 错因中文解释 | 12 个封闭错因标签均配中文含义说明 |
| 历史联动反馈 | 「这个错误你上次也犯过」——跨题目识别反复出错的知识点 |
| 复习提醒 | SM-2 间隔重复算法调度复习时点 |
| 能力画像 | 按知识点统计正确率，ECharts 雷达图 + 成长曲线 |
| 学习过程提示 | 基于编辑特征提示学习方式（AI 检测的学生端形态） |

### 2.2 教师端 · 教反馈

**定位：教学决策依据，不是管理工具。** 排课、考勤、通知、成绩核算均不在范围内。

| 能力 | 回答的教学问题 | 实现 |
|---|---|---|
| 班级知识点掌握度 | 我讲的学生掌握了吗？谁最弱？ | 复用现有聚合 SQL，换切片维度 |
| 班级错因分布 | 全班 60% 的 WA 都是边界条件 → 下节课讲这个 | 12 标签跨学生聚合 |
| 学生个人错因时间线 | 这个学生到底卡在哪？ | 按 user 聚合 |
| 提交审阅 | 代码 + 错因诊断 + 过程特征标记 | 三块汇合点 |
| 学情预警 | 哪些学生需要我关注？ | 阈值查询，自动标红 |

> **教师端走 Web 控制台，学生端保留 Electron 桌面应用**，两者共用同一后端。
> 理由：学生端的 Monaco + 本地编译是核心卖点（离线可用）；
> 教师端以读数据为主，做成 Web 页面成本最低、演示效果最好。
> `desktop/package.json` 已有 `dev:web` + `vite.config.web.ts`，这条路是现成的。

### 2.3 AI 使用检测 · 反馈的信号维度

**定位：过程证据提示，不是自动判定。**

| 出现位置 | 形态 |
|---|---|
| 学生端 | 「本次提交的编辑方式与你的习惯差异较大，建议独立完成」 |
| 教师端 | 提交列表中的「过程特征」标记，可展开看证据 |

**三层证据**（按可信度降序，当前实现聚焦第一层）：

| 层 | 依据 | 可信度 | 状态 |
|---|---|---|---|
| **第一层** | **编辑行为轨迹**：粘贴事件、编辑时间线、粘贴后改写比例 | 最高（客观可复现） | ✅ 已实现（分类信号，无概率、无分数） |
| 第二层 | 历史风格一致性：命名习惯、缩进、注释密度是否跃变 | 中（需 2–3 次基线） | 按需 |
| 第三层 | LLM 语义判断：是否超出该学生当前知识范围 | 兜底 | 按需 |

**原则**：
- **绝不输出单一的「AI 概率 87%」**。误判一个自己写代码的学生，
  比漏判一个用 AI 的学生严重得多——学生会失去信任，教师会弃用。
- 教师可**复核、可驳回**；学生端**只给提示不给分数**。
- 定位是**辅助教师判断，不是自动定罪**。

## 四、系统架构

```
┌──────────── 学生端 · Electron 桌面 ────────────┐  ┌──── 教师端 · Web 控制台 ────┐
│  Renderer (Vue 3 + TS)                        │  │  同一 Vue 应用（web 目标）   │
│  ├─ Monaco Editor + 编辑行为埋点               │  │  ├─ 班级学情看板            │
│  ├─ 分层反馈面板（错因引导逐层释放）           │  │  ├─ 错因分布聚合            │
│  ├─ 能力画像（ECharts）                        │  │  ├─ 学生个人错因时间线      │
│  └─ axios + WebSocket                          │  │  └─ 提交审阅（含过程标记）  │
│  Main 进程: spawn & 守护 sidecar、工具链探测   │  └──────────────┬──────────────┘
└───────────────────┬────────────────────────────┘                 │
                    └──────────────────┬───────────────────────────┘
                        localhost:随机端口 + Token
┌─────────────────────────────────────────────────────────────────┐
│  Sidecar (Python / FastAPI)                                     │
│  ├─ REST API + WebSocket 事件流                                  │
│  ├─ 错因分析 Agent（LLM Gateway + 工具循环 + 强校验）            │
│  │    └─ 输出：错因标签 / 错因说明 / 分层提示 / 修改方向          │
│  ├─ 过程特征提取（编辑行为轨迹 → 特征 → 反馈信号）                │
│  ├─ 学情聚合（知识点正确率 / 错因分布，按 user 与 tag 两种切片）  │
│  ├─ 复习调度（SM-2）                                             │
│  ├─ Sandbox: subprocess + 超时 + 内存上限（多语言）               │
│  └─ PostgreSQL + SQLAlchemy 2.0 + Alembic                        │
└─────────────────────────────────────────────────────────────────┘
```

### 架构决策要点

- **双进程分离**：UI（Electron）与计算（Python Sidecar）解耦，各自使用生态最擅长的技术栈
- **一后端两前端**：学生端 Electron + 教师端 Web 共用同一 FastAPI，避免两套业务逻辑
- **不引入消息队列**：不依赖 Redis / RabbitMQ / Celery，单机场景 asyncio 足够
- **模型可插拔**：LLM Gateway 统一 OpenAI 兼容协议，换模型只改配置不改代码
- **反馈分层在前端控制**：后端返回结构化的三段内容，前端控制释放时机——
  这样「释放几层」是可调的教学策略，而不是写死在数据里

**题目里的「智能体」指什么。** 题目是「基于智能体的编程课程学习过程分析与反馈
系统」，这里必须划清边界，否则两个方向都会翻车——说少了是漏报，说多了是过度声称：

- ✅ **指，且在主路径上**：一个工具调用智能体。模型自主决定是否调用
  `run_code` / `judge`，工具结果回传后再产出结构化诊断。学生提交后走的就是它
  （`records.analyse_submission` → `app/agent/pipeline.py` → `analyze_error`）。
- ✅ **已接入主路径，但默认关着**：LangGraph 状态图编排（S4）。判题路径现在由
  `ANALYSIS_PIPELINE` 选编排器（`direct` / `graph`），**默认值是 `direct`**，
  所以线上行为与接线前逐字一致；打开图是改一行 `.env` 的事。
  开关为什么默认关，两个具体理由：图一次分析最多 **4 次模型调用**
  （每轮 `max_attempts=2` × 自检回边 1 次），单次调用是 2 次，而这段开销发生在
  学生等 `judge_done` 的路上；更要紧的是 S2 的「20 题准确率 ≥ 60%」只能靠
  `pytest -m eval_set` 量（付费、按量计费，日常与夜间都不跑），
  **换了编排器就没人能回答准确率有没有退**。所以接线落地、开关留给人扳。
- ⚠️ **已实现并测试，但未接入主路径**：多智能体协作（S7）、知识库检索层（S5）、
  模型调用护栏（S10）。这三项**代码在仓库里、自动化测试全绿**，其中多智能体与
  护栏都用真实模型端到端验过。没接的原因是各自不同：S7 的产物是**提示与变式题**
  （另一条产品线，不是错因，接法还没定）；护栏要生效得把调用点换成
  `guarded_chat_completion`，而它会改变每次提交发出去什么、每次失败花多少钱。
  检索层在 `graph` 分支里是被调用的，只是默认分支走不到；另有一条：
  **Milvus 调用从未对着真实服务跑过**。
- ⬜ **真的没有**：Milvus 服务在本机起不来（Docker 不通，见 §六 阻塞项），因此
  RAG 只验到「连不上时正确降级」；LangSmith 追踪需要账号与 key，未接入。
- **统一口径**：这几项统一说成「**已实现并测试；编排线已接入判题主路径、默认仍走
  单次调用；检索未在真实向量库上验证**」。不要写成「系统已具备」——那会从
  「说没做」变成「说做了但演示不出来」，同样翻车；也不要反过来硬说「都没实现」，
  仓库里有可运行的图与测试、还有一条已经接好线的开关，被要求看代码时一样站不住。

### 阶段 7 的完成定义（打包）

打包最容易做成「本机跑得通」，所以完成定义一律按**目标机**写：

| # | 条目 | 判定 | 实测（2026-09-20） |
|---|---|---|---|
| 1 | sidecar 打成 **PyInstaller onedir** | 产物目录里的可执行文件能直接起，`GET /health` 返回 200 | ✅ `dist/algoforge-sidecar/algoforge-sidecar.exe` 直接起，1 秒内 `/health` 返回 `{"status":"ok"}` |
| 2 | **判题在打包后仍可用** | 真实编译 + 运行 + 输出比对跑通一次（AC 与 WA 各一）。这条最容易漏：打包时漏了编译器或临时目录，表现是 `/health` 正常但一判题就 CE | ✅ **三种语言都验过**：C++ / Python 各验 AC 与 WA；**Java 于 2026-09-20 补验，AC / CE / TLE 三条都在打包版上跑对**。一条命令可复现：`sidecar/.venv/Scripts/python.exe -u tools/verify_packaged_sidecar.py`。**并且因此抓出一个只在打包版出现的缺陷**，见下方 |
| 3 | 桌面端打成 **electron-builder** 安装包 | 装上后主进程能拉起打包版 sidecar（而不是 dev 的 uvicorn），走通一次提交 | ⬜ 未产出。本机沙箱禁止从 Bash 调用 PowerShell，而 electron-builder 的依赖收集器在 Windows 上硬编码走 `powershell.exe`，因此本机跑不出安装包——**配置本身没问题，是环境限制**，详见 `.workbuddy-ai/night-queue.md` 的 T3 |
| 4 | **密钥不进产物** | `.env` / `SIDECAR_TOKEN` 不写进包体；token 仍按既有约定运行时生成或由用户配置。打进去等于把共享密钥公开 | ✅ `dist/` 内 grep 不到任何 `.env`；打包脚本与 `electron-builder.yml` 两边都显式排除，改走 `ALGOFORGE_ENV_FILE` |
| 5 | 前置条件写清楚 | README 写明目标机需要什么（g++ 的路径配置、PostgreSQL 是否必需、非必需时的降级表现） | ✅ 见 §七「目标机前置要求」 |

**打包后 Python 判题曾经是坏的**（2026-09-20 修，提交 `b70ea20`）

第 2 条只验 C++ 是不够的，这次就漏掉了整条 Python 链路：

- 现象：打包版判 Python 一律返回 `{"status":"CE","compile_output":"Compilation timed out (>30s)"}`。
- 根因：`config.py` 的 `resolved_python_interpreter` 回退到 `sys.executable`。源码运行时
  那是 venv 的 python（正确）；**PyInstaller 冻结后它就是 sidecar 自己的 `.exe`**。
  于是语法检查变成「用 exe 去编译 python 文件」——exe 忽略不认识的参数、起了第二个
  HTTP 服务且永不退出，30 秒后超时判 CE。
- 为什么一直没暴露：**只在打包版出现，源码运行完全测不到**。
- 修法：冻结环境回退到 PATH 上的裸 `python`；显式 `PYTHON_INTERPRETER_PATH` 仍然优先。
  已补两个回归测试分别钉住冻结与非冻结两种默认。
- 教训：**「打包后判题仍可用」要逐语言验**。只验 C++ 会漏掉 Python 与 Java。

**打包版 Java 判题已补验**（2026-09-20）

上面那条教训原先只兑现了一半：C++ 与 Python 验过，**Java 一直挂着「未在打包版上
实测」**。现已在打包版上补齐三条：

- 起法：直接起 `dist/algoforge-sidecar/algoforge-sidecar.exe`，显式给
  `JAVA_COMPILER_PATH` / `JAVA_RUNTIME_PATH`（本机 JDK 8 不在 PATH 上）、
  `CPP_COMPILER_PATH`，`DATABASE_URL` 指向 SQLite，判题走 `record=false`
  所以**不需要 PostgreSQL**。
- 结果：`GET /api/v1/env-check` 报 `java available=true`、`javac 1.8.0_291`；
  `POST /api/v1/judge` 上 Java 三条分别判 **AC（2/2 用例）/ CE / TLE**。
- 已固定成脚本 `tools/verify_packaged_sidecar.py`（`--language java` 可单跑一种），
  三种语言 × AC/CE/TLE 共 9 条，一条命令跑完。**以后改打包脚本先跑它。**
- 顺带发现的真实缺陷：**Java 的 CE 输出是乱码**，见 §九。

**明确不做**（经方向讨论确定）：独立的 AI 检测服务、检测准确率研究、
完整教学管理功能（排课/考勤/通知/成绩）、真实部署上线。

**为什么不追求检测准确率**：检测准确性需要大量标注数据验证，
而本系统尚无真实教学场景数据。因此设计上定位为**过程证据提示 + 教师复核**，
不以准确率为目标——**可解释性优先于准确性**。
准确率的充分验证需要真实场景下的长期数据积累，属于后续工作。

## 七、快速开始

### 前置要求

- Node.js ≥ 20
- Python ≥ 3.11
- g++ 或 clang（MinGW / MSVC / clang 任一，路径通过 `.env` 配置）
- JDK（可选：**只在要判 Java 提交时**才需要，且必须是 JDK 而不是 JRE——`javac` 是判题用的那个工具；路径用 `JAVA_COMPILER_PATH` / `JAVA_RUNTIME_PATH` 配置）
- PostgreSQL

### 目标机前置要求（打包版）

上面那份是**开发机**的清单。打包版分发到别人机器上时条件不一样——sidecar 已经是
冻结的可执行文件，**目标机不需要装 Python 或 Node**；但**编译型语言的工具链必须由
目标机自己提供**，因为打包只冻结 Python，不会把 g++ 一起带走。

| 能力 | 目标机需要 | 缺了会怎样 |
|---|---|---|
| C++ 判题 | 自带 g++（或 clang），用 `CPP_COMPILER_PATH` 指过去 | 一判题就 CE，而 `/health` 仍然正常——看起来像判题器坏了 |
| Python 判题 | PATH 上有 `python`，或用 `PYTHON_INTERPRETER_PATH` 指过去 | Python 提交判 CE（打包版默认回退到 PATH 上的裸 `python`） |
| Java 判题 | 自带 **JDK**（要 `javac`，JRE 不够），用 `JAVA_COMPILER_PATH` / `JAVA_RUNTIME_PATH` 指过去 | Java 提交判 CE。✅ **已在打包版上实测**（2026-09-20：AC / CE / TLE 三条跑对）。注意本机 JDK 不在 PATH 上，**两个路径都要显式配置** |
| 错题本 / 画像 / 复习 | PostgreSQL | 这几项无持久化；**判题与运行照常可用**（实测不带 PG 也能判 AC） |

配置一律走环境变量，或用 `ALGOFORGE_ENV_FILE` 指向一个外部的 `.env`——
打包产物里**不含** `.env`，这是刻意的，见 §六 完成定义第 4 条。

### 配置

```bash
cd sidecar
cp .env.example .env
```

然后编辑 `.env`，**至少**要改这一项——指向你本机的 g++：

```env
CPP_COMPILER_PATH=D:\path\to\ucrt64\bin\g++.exe
```

> 留空写作 `CPP_COMPILER_PATH=g++` 也可以，此时从 PATH 解析。
> `CPP_COMPILER_BIN_DIR` 默认取 g++ 所在目录（MinGW 运行 DLL 需要它），一般无需设置。
>
> `SIDECAR_PORT` / `SIDECAR_TOKEN` 留空 = 启动时随机生成。
> 正常启动路径下无需设置：Electron 主进程会自己挑一个空闲端口并生成 Token，
> 再通过 IPC 传给渲染进程（见 `desktop/src/main/sidecar.ts`）。
> 只有想手动 `curl` 调试后端时才需要显式固定端口。

LLM 相关配置见 `.env.example` 内的注释（provider 切换、token 上限、超时，
以及推理模型的特殊取值建议）。

### 测试

```bash
cd sidecar

# 日常用这条：跳过 eval_set
env -u PYTHONPATH python -m pytest ../tests -q -m "not eval_set"

# 只在确实要测真实模型时跑：会调用付费端点、按测试计费、结果不可复现
env -u PYTHONPATH python -m pytest ../tests -q -m eval_set
```

三点说明，都是实测踩过的：

- **`env -u PYTHONPATH` 不能省。** 否则 `sitecustomize.py` 会让清理阶段的
  `Path.unlink` 抛 `SystemExit(1)`，表现为一大批与本次改动无关的失败。
- **默认不要跑全量。** `eval_set` 那批会真的请求 LLM 服务，既计费又不可复现——
  **不要把它当成「跑个全量」的顺手选项**。
- 慢的是**真实 C++ 编译**（单文件约 88 秒），不是 LLM。
- **进程创建开销可能退化到 5 秒以上**，那时一切真实执行都会 TLE。先用
  `python -c "import subprocess,time;t=time.perf_counter();subprocess.run(['whoami']);print(time.perf_counter()-t)"`
  量一下：正常是几十毫秒，2026-09-19 实测一度是 **5.2 秒**（`CreateProcess`
  被安全软件挂钩，与本仓库无关）。判题的上限是 5 秒，所以那时候**正确的代码
  也会判 TLE**——这是机器的问题，不是判题器的问题。断言「程序正确」的测试因此
  用 `conftest.EXEC_TIME_LIMIT`（30 秒）作为预算；「超时会被杀」由
  `test_timeout` / `test_judge_tle` 用 1 秒上限各自覆盖，不受影响。

前端单元测试 2026-09-19 接入 Vitest（`AGENTS.md` 锁定的框架），44 个用例：

```bash
cd desktop
./node_modules/.bin/vitest run   # 单次
./node_modules/.bin/vitest       # 监听
```

⚠️ **本机请直接调 `./node_modules/.bin/vitest`，不要用 `npm run test`。**
2026-09-19 实测：`npm run test` 在这台机器上**静默失败**——退出码 1，且
**一个字都不输出**（连 vitest 的启动横幅都没有）。项目其它 `npm run` 脚本
同样如此，所以是本机 npm 的问题，不是命令写错了。`package.json` 里的
`test` / `test:watch` 留给 CI 和其它机器用。

覆盖两件事：

- **api 层的聚合规则**——`foldVerdicts` 的「通过是粘性的」（AC 之后再 WA 仍
  算通过，因为界面问的是「有没有解出过」，不是「最后一次好不好」）、
  `pickDefaultLanguage` 的兜底（C++ 不可用时不选它，选了就是一片 CE）。
- **判题流的事件时序**——这条是一条真实故障的回归测试。客户端曾把
  `judge_done` 当成「流结束」立刻关闭 WebSocket，而智能体分析的事件走
  **同一条**连接，于是 WA 之后永远看不到错因，且被读成「分析没跑」。现在由
  `judge_done.analysing` 决定何时关，`ws.spec.ts` 钉住的就是这个时刻。
- **分层释放的组件行为**（`LayeredFeedback.spec.ts`，7 个用例）——api 层测不到
  的部分：一次给几层。它坏了的表现不是报错，而是学生多看到一层本该自己想的
  答案，所以只能真渲染一遍才抓得住。钉住的是三条：初始一层不给、空段被跳过、
  **新诊断自动收起**（不收起就会把上一题的解答摊在学生面前）。
- **诊断与工具结果怎么呈现**（`OutputPanel.spec.ts`，7 个用例）——这个组件
  **不拥有状态**（父组件推事件进来，它只推导显示什么），所以能脱离 WebSocket
  纯靠 props 测。钉住的四条都是「坏了只是该出现的没出现」：分析失败时不许渲染
  那张「以上是全部反馈」的**空卡片**（真出过这个 bug）、工具那一行要说
  **返回了什么**（`输出：21`）而不是调用了什么、判题跑完但分析还在跑时必须
  仍旧显示「分析中…」（P2-8 修的那条）、试运行要标明未记录。
- **判定到颜色的映射**（`VerdictBadge.spec.ts`，4 个用例）——这个组件存在的
  理由就是消灭那份映射的四份拷贝。最要紧的是**降级**：状态是 WebSocket 来的
  字符串，后端将来加一个判定（或打错字）时，徽章要渲染成中性灰并**原样显示
  那个字符串**——空白比错颜色更糟，因为它读起来像「这次没有结果」。

⚠️ 组件测试**只覆盖三个组件**：`LayeredFeedback`（分层释放）、`OutputPanel`
（诊断与工具结果怎么呈现）、`VerdictBadge`（判定到颜色的映射）。其余组件
（编辑器、教师看板、雷达图等）依旧只有人眼走查过，类型检查 + 单测都证明不了
「页面长得对不对、点了有没有反应」。

写组件测试时的两个坑（都实测踩过）：

- **必须 `attachTo: document.body`。** 组件用 `v-show` 控制分层，断言要看
  **可见性**而不是元素存不存在；而 `isVisible()` 读 computed style，jsdom
  对**游离节点**算不出值，于是已释放的段落也会被判不可见——不挂上去，测试会
  「状态明明对了却失败」，且看不出错在哪。
- **环境要 opt-in。** 全局仍是 node（api 层测试不需要 DOM，套上白付开销），
  需要 DOM 的 spec 在文件首行写 `// @vitest-environment jsdom`。
  `vitest.config.ts` 里的 `vue()` 插件是另一处必需项：没有它，import `.vue`
  会被当成语法错误。

### 数据库说明

`DATABASE_URL` 是生产 PostgreSQL DSN（`postgresql+asyncpg`）。
API 路由是同步的，`app/db.py` 会把 asyncpg URL 自动改写为
`psycopg` 同步驱动——所以**不会**再静默降级到 SQLite。
同步路由需要指向另一个 DSN 时，用 `DATABASE_URL_SYNC` 覆盖。
测试通过 monkeypatch `get_session` 使用 SQLite，无需真实 PG——**但这也意味着
SQLite 不会替你发现方言问题**（它默认不强制外键，函数名也不同）。

要跑真 PostgreSQL：

```bash
./tools/pg_verify.sh   # 起 PG → 迁移到 head → 跑聚合 SQL → 干净停止
```

需要 `D:\pg` 的 zip 版 PostgreSQL 17.6（免安装、无服务、无管理员）。脚本头部
写了三个必知的坑，其中最容易踩的是：**PG 不跨 shell 调用存活**，所以启动与
使用必须在同一次调用内完成——脚本就是那一次调用，别拆开手工跑。

## 八、工程约定

技术栈约束、工程红线与开发规范见 **[`AGENTS.md`](./AGENTS.md)**，动工前必读。

几条最容易违反的：

1. **所有 LLM 输出必须过 JSON Schema 校验**，不合规不入库
2. **数据库迁移走 Alembic**，不手写 `ALTER TABLE`
3. **新增字段必须 nullable 或有 `server_default`**，否则现有测试会一起崩
4. **Prompt 不硬编码业务逻辑**，全部走 `sidecar/app/prompts/` 模板文件
5. **换模型不改代码**，只改 LLM Gateway 配置

| **无检测验证集** | AI 使用检测缺少人工标注样本，因此不以准确率为目标 |
