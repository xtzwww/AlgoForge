## 一、项目定位

### 要解决的问题

线上编程教学普及后，暴露出两个痛点：

1. **学情不可见** —— 教师只看到最终提交结果，看不到学生「怎么学、卡在哪」；
     
   现有平台的学情分析多停留在登录时长、视频观看等浅层行为指标。
2. **反馈无效** —— 传统 OJ 只给 AC / WA 判定，不给「为什么错、怎么想」；
     
   学生拿到 WA 之后纠错成本全压在自己身上，且同样的错误会反复犯。

本系统同时应对这两点：**让学习过程可观测，让反馈可分层、可追溯。**

### 核心思路（升级后的主线）

> **以「反馈」组织整个系统**，而不是把功能平铺成「学生端 + 教师端 + 检测」三块。

```
                    学习过程数据
        （提交结果 + 编辑行为轨迹 + 历史记录）
                          │
          ┌───────────────┴───────────────┐
          ▼                               ▼
    给学生 · 学反馈                  给教师 · 教反馈
  分层释放的错因引导              班级知识点掌握度
  「这题你卡在哪」                「全班弱在哪」
  「这个错误你犯过 N 次」         「下节课该讲什么」
          │                               │
          └───────────────┬───────────────┘
                          ▼
                AI 使用检测（信号维度）
       学生端 =「学习过程提示」，教师端 =「过程特征标记」
```

**AI 检测为什么是「一个维度」而不是「一个模块」**：
  
检测的目的不是抓学生，而是**给学生一个关于自己学习方式的反馈**。
  
它融入上面两条链路，因此不需要独立的检测服务，也不以「检测准确率」为目标。

### 差异化：过程数据是别人拿不到的

本系统自带 Monaco 编辑器，因此可以采集**编辑过程**：
  
什么时候粘贴的、粘贴后改了多少、编辑节奏如何、有没有反复调试。

|       | 通用检测工具（GPTZero / Turnitin） | 本系统                    |
| ----- | -------------------------- | ---------------------- |
| 能看到什么 | 只看最终文本                     | **文本 + 写作过程**          |
| 判据    | 统计特征（困惑度、突发性）              | **行为轨迹（客观可复现、可向学生解释）** |
| 适用场景  | 自然语言                       | **编程作业（代码）**           |

> **粘贴 80 行后零修改直接提交**（代写）与**粘贴后大量改写、反复试错**（参考题解），
>   
> 在纯文本上看起来一样，在过程数据上完全不同。
>   
> 这个区分度是**自有编辑器才具备的数据优势**，也是本设计的创新点所在。

## 二、系统功能

### 2.1 学生端 · 学反馈

**分层释放的错因引导（核心功能）**

现有实现把 AI 诊断的三段内容一次性倾泻给学生（`【错在哪】【提示】【怎么改】`），
  
学生往往直接看「怎么改」，跳过思考环节。本系统改为**分层释放**：

```
提交（WA）
   ↓
【第一层】错在哪          指出实际错因，用学生能读的中文说明
   ↓  点「还是不会，给点提示」
【第二层】提示            给方向，仍不给答案
   ↓  点「还是不会，直接看怎么改」
【第三层】怎么改          完整的修改建议
   ↓  点「重新自己想」
（收起，回到只看第一层）
```

**教学设计依据**：支架式教学（scaffolding）——逐步撤除支持，
  
让学生尽可能自主完成。这是教育学理论在系统里的具体落地。

**三个实现上的取舍**（都是刻意的）：

- **初始什么都不显示**，连「错在哪」也在按钮后面。若默认展开第一层，
    
  「还是不会」就退化成「显示剩余内容」，对思考的推动弱得多。
- **释放层数按实际内容算**，不是固定三层。模型跳过某一节时按钮直接跳到下一节，
    
  不会点开一个空面板 —— 打开门看见空房间会被读成 bug。
- **释放进度不持久化**，离开页面再回来重新从第一层开始。门槛是一次自我评估，
    
  隔天回来看同一道题的是另一个学习者；存下「已看过答案」等于让这次回访失去意义。

**其余学生端能力**

| 能力      | 说明                                                   |
| ------- | ---------------------------------------------------- |
| 在线编程与提交 | Monaco 编辑器（自定义主题、多语言切换）+ 一键编译运行                      |
| 多语言判题   | C++ / Python / Java，判定 AC / WA / TLE / MLE / CE / RE |
| 错题本     | 自动归档、分析状态可见、失败可重试、按错因与知识点筛选                          |
| 错因中文解释  | 12 个封闭错因标签均配中文含义说明                                   |
| 历史联动反馈  | 「这个错误你上次也犯过」——跨题目识别反复出错的知识点                          |
| 复习提醒    | SM-2 间隔重复算法调度复习时点                                    |
| 能力画像    | 按知识点统计正确率，ECharts 雷达图 + 成长曲线                         |
| 学习过程提示  | 基于编辑特征提示学习方式（AI 检测的学生端形态）                            |

### 2.2 教师端 · 教反馈

**定位：教学决策依据，不是管理工具。** 排课、考勤、通知、成绩核算均不在范围内。

| 能力        | 回答的教学问题                     | 实现               |
| --------- | --------------------------- | ---------------- |
| 班级知识点掌握度  | 我讲的学生掌握了吗？谁最弱？              | 复用现有聚合 SQL，换切片维度 |
| 班级错因分布    | 全班 60% 的 WA 都是边界条件 → 下节课讲这个 | 12 标签跨学生聚合       |
| 学生个人错因时间线 | 这个学生到底卡在哪？                  | 按 user 聚合        |
| 提交审阅      | 代码 + 错因诊断 + 过程特征标记          | 三块汇合点            |
| 学情预警      | 哪些学生需要我关注？                  | 阈值查询，自动标红        |
| 出题与作业管理   | 我要留什么题、什么时候交？              | 题目增删改查 + 复制、作业发布/复制/截止 |
| 花名册维护     | 把学生加进来                        | 单个添加 + 名单批量导入（CSV 粘贴） |
| 学生成绩单     | 这个学生每份作业做了多少？             | 逐作业进度，**含没交的也列出来** |
| AI 辅助强度    | 这份作业允许 AI 帮到什么程度？           | 五档，发布作业时设定；用量留痕可查 |

> **教师端走 Web 控制台，学生端保留 Electron 桌面应用**，两者共用同一后端。
>   
> 理由：学生端的 Monaco + 本地编译是核心卖点（离线可用）；
>   
> 教师端以读数据为主，做成 Web 页面成本最低、演示效果最好。
>   
> `desktop/package.json` 已有 `dev:web` + `vite.config.web.ts`，这条路是现成的。

#### AI 辅助强度：五档，由发布作业的老师决定

学生做题时，编辑器旁边可以有一个 AI 助手。**帮到什么程度由老师定**，
学生不能自己调档——档位存在作业上，前端传的是 `assignment_id`，
档位在服务端查。越档的请求在**调用模型之前**就被拒绝。

| 档 | 学生看到的名字 | 能力                          |
| -- | ------- | --------------------------- |
| 一  | 本机补全    | 查本机词表补全，**不联网、不调用任何模型**      |
| 二  | AI 补全   | 联网模型补全                      |
| 三  | 答疑      | 编辑器旁的对话框，可提问，**只给提示、不能写进代码** |
| 四  | 代写片段    | AI 可以写一段代码，学生决定要不要采纳         |
| 五  | 完整解法    | 连整题解法都能给                     |

**能力的递增是设计出来的**：档位数字越大，能力集合越大，绝不出现
「三档能做的事四档反而不能」。三档额外有一道内容门——如果模型的回复
看起来像代码（代码块或函数定义），会被降级成散文提示再交给学生。

**留痕**：每次请求补全 / 提问 / 采纳 AI 写的代码 / 请求完整解法都记一行
（`assistance_usage` 表），老师能看到哪个学生、哪份作业用了多少次。
**只记动作和次数，不记对话内容**——这是辅助教学判断，不是抓人。

### 2.3 AI 使用检测 · 反馈的信号维度

**定位：过程证据提示，不是自动判定。**

| 出现位置 | 形态                          |
| ---- | --------------------------- |
| 学生端  | 「本次提交的编辑方式与你的习惯差异较大，建议独立完成」 |
| 教师端  | 提交列表中的「过程特征」标记，可展开看证据       |

**三层证据**（按可信度降序，当前实现聚焦第一层）：

| 层       | 依据                            | 可信度          | 状态                  |
| ------- | ----------------------------- | ------------ | ------------------- |
| **第一层** | **编辑行为轨迹**：粘贴事件、编辑时间线、粘贴后改写比例 | 最高（客观可复现）    | ✅ 已实现（分类信号，无概率、无分数） |
| 第二层     | 历史风格一致性：命名习惯、缩进、注释密度是否跃变      | 中（需 2–3 次基线） | 按需                  |
| 第三层     | LLM 语义判断：是否超出该学生当前知识范围        | 兜底           | 按需                  |

**原则**：

- **绝不输出单一的「AI 概率 87%」**。误判一个自己写代码的学生，
    
  比漏判一个用 AI 的学生严重得多——学生会失去信任，教师会弃用。
- 教师可**复核、可驳回**；学生端**只给提示不给分数**。
- 定位是**辅助教师判断，不是自动定罪**。

## 四、系统架构

```
┌──────────── 学生端 · Electron 桌面 ────────────┐  ┌──── 教师端 · Web 控制台 ────┐
│  Renderer (Vue 3 + TS)                        │  │  同一 Vue 应用（web 目标）   │
│  ├─ Monaco Editor + 编辑行为埋点               │  │  ├─ 班级学情看板            │
│  ├─ 分层反馈面板（错因引导逐层释放）           │  │  ├─ 错因分布聚合            │
│  ├─ 能力画像（ECharts）                        │  │  ├─ 学生个人错因时间线      │
│  └─ axios + WebSocket                          │  │  └─ 提交审阅（含过程标记）  │
│  Main 进程: spawn & 守护 sidecar、工具链探测   │  └──────────────┬──────────────┘
└───────────────────┬────────────────────────────┘                 │
                    └──────────────────┬───────────────────────────┘
                        localhost:随机端口 + Token
┌─────────────────────────────────────────────────────────────────┐
│  Sidecar (Python / FastAPI)                                     │
│  ├─ REST API + WebSocket 事件流                                  │
│  ├─ 错因分析 Agent（LLM Gateway + 工具循环 + 强校验）            │
│  │    └─ 输出：错因标签 / 错因说明 / 分层提示 / 修改方向          │
│  ├─ 过程特征提取（编辑行为轨迹 → 特征 → 反馈信号）                │
│  ├─ 学情聚合（知识点正确率 / 错因分布，按 user 与 tag 两种切片）  │
│  ├─ 复习调度（SM-2）                                             │
│  ├─ Sandbox: subprocess + 超时 + 内存上限（多语言）               │
│  └─ PostgreSQL + SQLAlchemy 2.0 + Alembic                        │
└─────────────────────────────────────────────────────────────────┘
```

### 架构决策要点

- **双进程分离**：UI（Electron）与计算（Python Sidecar）解耦，各自使用生态最擅长的技术栈
- **一后端两前端**：学生端 Electron + 教师端 Web 共用同一 FastAPI，避免两套业务逻辑
- **不引入消息队列**：不依赖 Redis / RabbitMQ / Celery，单机场景 asyncio 足够
- **模型可插拔**：LLM Gateway 统一 OpenAI 兼容协议，换模型只改配置不改代码
- **反馈分层在前端控制**：后端返回结构化的三段内容，前端控制释放时机——
    
  这样「释放几层」是可调的教学策略，而不是写死在数据里

  换实例 → 读出」。中间修掉两个真 bug：① `PostgresSaver.from_conn_string(uri)`

  `get_tuple()` 报 `AttributeError`；② 就算 `__enter__()` 进去也不行——它内部

  开连接**再 `PostgresSaver(conn)` / `PostgresStore(conn)`（`_open_postgres()` 就是

**打包后 Python 判题曾经是坏的**（2026-09-20 修，提交 `b70ea20`）

第 2 条只验 C++ 是不够的，这次就漏掉了整条 Python 链路：

- 现象：打包版判 Python 一律返回 `{"status":"CE","compile_output":"Compilation timed out (>30s)"}`。
- 根因：`config.py` 的 `resolved_python_interpreter` 回退到 `sys.executable`。源码运行时
    
  那是 venv 的 python（正确）；**PyInstaller 冻结后它就是 sidecar 自己的 `.exe`**。
    
  于是语法检查变成「用 exe 去编译 python 文件」——exe 忽略不认识的参数、起了第二个
    
  HTTP 服务且永不退出，30 秒后超时判 CE。
- 为什么一直没暴露：**只在打包版出现，源码运行完全测不到**。
- 修法：冻结环境回退到 PATH 上的裸 `python`；显式 `PYTHON_INTERPRETER_PATH` 仍然优先。
    
  已补两个回归测试分别钉住冻结与非冻结两种默认。

**Java 编译错误的乱码**（2026-09-20 修）

- 现象：Java 提交判 CE 时，学生看到的是
    
  `Main.java:2: ����: �Ƿ��ı���ʽ��ʼ`。**判定本身是对的**（该判 CE 仍判 CE），
    
  坏的只是可读性——但那正是学生唯一能读的报错。C++ 与 Python 不受影响。
- 根因：`javac` 按**宿主区域**输出本地化诊断，中文 Windows 上是 GBK；而沙箱统一
    
  按 UTF-8 解码（`compiler.py` 的 `encoding="utf-8" / errors="replace"`）。
    
  `_build_env` 只给 Python 设了 `PYTHONIOENCODING`，JVM 不读这个变量。
- 修法：给 Java 的两条命令都钉上 `-Duser.language=en -Duser.country=US`
    
  （javac 侧要带 `-J` 前缀），报错变英文 ASCII，与 g++ / CPython 一致。
    
  实现在 `languages._JAVA_LOCALE_FLAGS`。
- **票里给的另一个候选修法被实测否决**：`-J-Dfile.encoding=UTF-8` 也能消掉乱码，
    
  但它会连带让 `javac` 按 UTF-8 读**源码**，而「Java 提交打印中文」目前能正确
    
  往返**只因为** javac 把 UTF-8 源码误读成 GBK、运行期又把同样的字节写回来。
    
  钉成 UTF-8 会打断这个往返：`你好世界` 变成 `c4e3bac3cac0bde7`，
    
  **正确解被判 WA**。已加回归测试钉住这一点。
- 验证：源码路径与**打包版**（`tools/verify_packaged_sidecar.py`，Java CE 首行
    
  现为 `Main.java:2: error: illegal start of expression`）双双通过；
    
  三种语言 × 三条判定 9/9 仍符合预期。

**重建打包产物：`build_sidecar.sh` 一直是空操作**（2026-09-20 修）

**「`langgraph` / `pymilvus` 没进产物」这个诊断是错的**（2026-09-21 推翻）

上面这段原先还跟着一句「仍未打包进去的：`langgraph` 与 `pymilvus` 的**包体**……
PyInstaller 只跟静态 import，所以跟不到」。**这句话是错的**，而且错得很有代表性：
它是从「这两处在源码里是函数体内 import」**推**出来的，**没有人解包数过**。

实际解出那份 113 MB 产物的 `PYZ` 归档逐个点名：

| 包 | PYZ 里的模块数 | 说明 |
|---|---|---|
| `langgraph` | 126 | 含 `langgraph.graph`、`langgraph.checkpoint.base` |
| `pymilvus` | 68 | **含 `pymilvus.milvus_client.milvus_client`**——正是 `MilvusClient` 所在 |
| `langsmith` | 229 | |
| `psycopg` | 80 | |
| `app.agent.graph` / `app.agent.pipeline` | 各 1 | 被懒导入的那两个模块本身也在 |

**PyInstaller 扫的是字节码，函数体内的 `IMPORT_NAME` 一样跟得到**，所以「懒导入
就收不到」不成立。

**那为什么还要改**：因为收得到靠的是**字节码扫描这个偶然行为**。任何一处改成
`importlib.import_module("...")`、或把名字挂在 `__getattr__` 后面转发，扫描就断，
而断了的症状是**打包时全绿、运行时才 `ImportError`**——最难查的一类。所以现在把
这 5 个模块写进 `build_sidecar.sh` 的 `--hidden-import`（S4 图 / S7 三智能体 /
`pymilvus` / S8 的两个 PG backend），把「它们必须进包」变成**打包期的契约**。
代价是零：它们本来就在产物里。

**顺带量出一个 81 MB 的坑**：加完 `--hidden-import pymilvus` 产物从 113 MB
**涨到 194 MB**——多出来的全是 `pyarrow/`（81 MB）+ `pyarrow.libs/`（1 MB）。
因为显式声明会让 PyInstaller 扫到 `pymilvus/bulk_writer/`，而那里是**模块级**
`import pyarrow`（`buffer.py:21`、`constants.py:16`）。bulk_writer 是 pymilvus 的
「批量导入」功能，本项目只用 `MilvusClient` 建库与检索，永远不碰它；
`pymilvus/client/type_info.py` 自己还专门注释了「不 import pyarrow」。

⚠️ **但「屏蔽 pyarrow」这个结论在 2026-09-22 被推翻了**，而且推翻得很有教育意义：
当时加 `--exclude-module pyarrow` 后产物回到 113 MB，验证方式是
`from pymilvus import MilvusClient` ——**它成功，于是记成「结论：屏蔽后仍可用」**。
那句话只覆盖了「连 Milvus **服务**」这条路。本轮决定把**内嵌**向量库
（`milvus-lite`）打进产物后，`import milvus_lite` 立刻炸：

```
ModuleNotFoundError: No module named 'pyarrow'
```

来源是 `milvus_lite/engine/collection.py` 的**模块级** `import pyarrow`——而它还会
被 pymilvus 包成一句极具误导性的
「milvus-lite is required for local database connections，请 pip install
`pymilvus[milvus_lite]`」，看着像依赖没装，实际是**我们把它的依赖排除了**。

→ **教训：`--exclude-module` 的验证必须覆盖「所有会用到它的路径」，而不是当前
默认路径。** 默认路径是最不容易暴露问题的那条。所以现在 `pyarrow` 与
`milvus_lite` / `faiss` 一起**必须进包**，产物 258 MB。

**冻结产物能不能 import 整条分析链路，现在有运行时证据**：打包入口加了
`--self-check`（无模型调用、无数据库、无 Milvus 连接），逐个 import
S4 图 / S7 三智能体 / S5 检索层（`retriever` + `embedder` + `reranker`）/
`pymilvus` / S8 的两个 PG backend，**再真正 `build_analysis_graph()` 一次**
（只 import 走不到 `StateGraph` 的组装代码），最后**按真实调用方式装配检索**
（`from app.rag import build_embedder, build_reranker, build_retriever`）。
打包版实测 **10/10 通过**；它也能在源码树上跑，用来区分「venv 坏了」与「包坏了」。

⚠️ **这份自检在 2026-09-22 之前是会漏报的**，值得记一笔：它当时只查
`app.rag.retriever`，而 `app/rag/__init__.py` 在**顶层** re-export 了
`embedder` 与 `reranker`——`pipeline.py` 的 `from app.rag import build_embedder`
一旦因此抛 `ImportError`，会被它自己那个 `except ImportError` 吃掉，检索
**静默关闭**（一行 info 日志，不报错，界面也看不出来），而自检照样 7/7 全绿。
实测踩到过一次：产物 09-21 10:36 打的，这两个模块 09-22 凌晨才加进去。
→ **教训：自检全绿只说明「它查的那几项在」，不等于「包是新的」。**
判断产物新旧要 `stat` mtime 跟源文件比。

**还有两个自检，覆盖自检覆盖不到的层面**（都要联网，所以单独开关、不默认跑）：

| 开关 | 查什么 | 依赖 |
|---|---|---|
| `--self-check-embedding` | 向量模型端点本身：provider/model/base_url、密钥在不在、调一次拿回多少维 | 只要模型端点 |
| `--self-check-retrieval` | 语料在不在、向量库在不在、**真的检索一次**并列出取回的卡片 | 模型端点 + 语料 |

上线后「分析里没有参考资料」时，这两个能二分定位：**先跑 embedding 那个**——
它绿说明端点没问题、问题在索引侧；它红就直接告诉你端点是哪个、连不上为什么。

⚠️ **打包版检索曾经整整一轮静默失效，根因是配置而不是代码**，值得记一笔。
症状是 `[WinError 10061] 由于目标计算机积极拒绝，无法连接。`——看着像 Milvus
连不上，实际是**向量模型端点没配**：`.env` 里配的是云端端点，源码树读得到；
而产物**刻意不带 `.env`**（里面有密钥），于是落回 `config.py` 的默认值
`ollama` + `http://127.0.0.1:11434`（本机 Ollama，没开）。这个异常被检索的
「出错即返回空上下文」约定吞成一行 warning，**界面上只表现为「分析里没有参考
资料」**，完全看不出是配置问题。

所以打包版交付时要明确一件事：**产物需要外部提供向量模型的两个选择之一**
（云端四个环境变量，或本机跑着 Ollama），`.env.example` 里已写清，详见
`sidecar/.env.example` 的 RAG 段。

顺带修掉一个只在打包版出现的崩溃：Windows 控制台默认代码页是 GBK，
`--self-check-embedding` 里的 `↳` 字符 GBK 收不下，直接
`UnicodeEncodeError` 把进程带走——**报错指向 `print`，看起来像被检查的东西坏了**。
修法是在入口把 stdout/stderr 重配成 UTF-8（`errors="replace"`），而不是躲避
特殊字符。

**2026-09-22：把内嵌向量库与语料打进产物，打包版检索从「静默失效」变成「可用」**

这一轮的起因是解包复核：产物里的 `app.rag.*` 只有 5 个模块，源码有 7 个——
少的正是 `embedder` 与 `reranker`。于是做了三件事：

**① 让数据文件跟着进包。** 题目语料 / 知识卡片 / 评估集三处的默认路径原先都是
`Path(__file__).resolve().parents[N]`，**冻结后 `__file__` 指向产物内部**，于是
打包版既找不到题目也找不到知识卡片。修法是引入 `app.config.DATA_ROOT`：源码树
按 `__file__` 算，冻结时用 `sys._MEIPASS`（onedir 下就是 `_internal/`，也正是
`--add-data` 的目标基准），另给 `ALGOFORGE_DATA_ROOT` 作为逃生口。
`build_sidecar.sh` 里对应加了三条 `--add-data`。⚠️ 目标**不能写 `../corpus`**：
PyInstaller 会拒绝（`DEST_DIR must not point outside of application's top-level
directory`）。

**② 决定把 `milvus-lite` 打进产物。** 两条路里选了内嵌（另一条是让目标机
自己跑 Milvus 服务，本机 Docker 不通）。代价是体积 113 → 258 MB，换来的是
**目标机开箱即用**——不需要 Docker、不需要另起服务。为此踩满三个连环坑：
`milvus_lite` 要 `faiss`、要 `pyarrow`（见上）、还要 `--copy-metadata "milvus-lite"`
（`milvus_lite/_version.py` 的 `get_version()` 先找 `pyproject.toml`——打包后没有，
再退回 `importlib.metadata.version()`，而 PyInstaller 默认不带 `*.dist-info`；
报错是 `PackageNotFoundError: No package metadata was found for milvus-lite`）。

**③ 给向量库目录做自动创建 + 索引自动重建。** `build_retriever` 在打开文件型
Milvus 前会建父目录（新检出与全新产物都没有 `sidecar/data/`，而原报错
「Open local milvus failed, dir: ... not exists」读起来像安装坏了）；`pipeline`
在检索**空结果**时调一次 `_build_index_and_search` 自动建索引重试——因为索引是
派生数据（gitignored），新机器上必然为空。这条自愈在产物上被**真实触发过**
（首跑日志里能看到 `collection ... does not exist` → 建索引 → 取回 3 张卡片）。

最后那个「向量模型端点没配」的坑见上文——它才是整轮排查里最费时间的一环，
因为错误信息（`WinError 10061`）指向的方向完全是错的。

**明确不做**（经方向讨论确定）：独立的 AI 检测服务、检测准确率研究、
  
完整教学管理功能（排课/考勤/通知/成绩）、真实部署上线。

**为什么不追求检测准确率**：检测准确性需要大量标注数据验证，
  
而本系统尚无真实教学场景数据。因此设计上定位为**过程证据提示 + 教师复核**，
  
不以准确率为目标——**可解释性优先于准确性**。
  
准确率的充分验证需要真实场景下的长期数据积累，属于后续工作。

## 七、快速开始

### 前置要求

- Node.js ≥ 20
- Python ≥ 3.11
- g++ 或 clang（MinGW / MSVC / clang 任一，路径通过 `.env` 配置）
- JDK（可选：**只在要判 Java 提交时**才需要，且必须是 JDK 而不是 JRE——`javac` 是判题用的那个工具；路径用 `JAVA_COMPILER_PATH` / `JAVA_RUNTIME_PATH` 配置）
- PostgreSQL

### 目标机前置要求（打包版）

上面那份是**开发机**的清单。打包版分发到别人机器上时条件不一样——sidecar 已经是
  
冻结的可执行文件，**目标机不需要装 Python 或 Node**；但**编译型语言的工具链必须由
  
目标机自己提供**，因为打包只冻结 Python，不会把 g++ 一起带走。

| 能力            | 目标机需要                                                                         | 缺了会怎样                                                                                       |
| ------------- | ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| C++ 判题        | 自带 g++（或 clang），用 `CPP_COMPILER_PATH` 指过去                                     | 一判题就 CE，而 `/health` 仍然正常——看起来像判题器坏了                                                         |
| Python 判题     | PATH 上有 `python`，或用 `PYTHON_INTERPRETER_PATH` 指过去                             | Python 提交判 CE（打包版默认回退到 PATH 上的裸 `python`）                                                   |
| Java 判题       | 自带 **JDK**（要 `javac`，JRE 不够），用 `JAVA_COMPILER_PATH` / `JAVA_RUNTIME_PATH` 指过去 | Java 提交判 CE。✅ **已在打包版上实测**（2026-09-20：AC / CE / TLE 三条跑对）。注意本机 JDK 不在 PATH 上，**两个路径都要显式配置** |
| 错题本 / 画像 / 复习 | PostgreSQL                                                                    | 这几项无持久化。⚠️ **「判题照常可用」只在 `DATABASE_URL` 指向 SQLite 时成立**（打包冒烟就是这么测的，`record=false` 下实测能判 AC）；**若 `DATABASE_URL` 指向 PostgreSQL 而 PG 没起，表现是挂住而不是降级**——详见「启动开发环境」里那条「数据库没起来会怎样」                                                       |

配置一律走环境变量，或用 `ALGOFORGE_ENV_FILE` 指向一个外部的 `.env`——
  
打包产物里**不含** `.env`，这是刻意的，见 §六 完成定义第 4 条。

### 配置

```bash
cd sidecar
cp .env.example .env
```

然后编辑 `.env`，**至少**要改这一项——指向你本机的 g++：

```env
CPP_COMPILER_PATH=D:\path\to\ucrt64\bin\g++.exe
```

> 留空写作 `CPP_COMPILER_PATH=g++` 也可以，此时从 PATH 解析。
>   
> `CPP_COMPILER_BIN_DIR` 默认取 g++ 所在目录（MinGW 运行 DLL 需要它），一般无需设置。
>
> `SIDECAR_PORT` / `SIDECAR_TOKEN` 留空 = 启动时随机生成。
>   
> 正常启动路径下无需设置：Electron 主进程会自己挑一个空闲端口并生成 Token，
>   
> 再通过 IPC 传给渲染进程（见 `desktop/src/main/sidecar.ts`）。
>   
> 只有想手动 `curl` 调试后端时才需要显式固定端口。

LLM 相关配置见 `.env.example` 内的注释（provider 切换、token 上限、超时，
  
以及推理模型的特殊取值建议）。

### 启动开发环境

```bash
# 1. 数据库（AGENTS.md §一 锁定业务数据库为 PostgreSQL，不用 SQLite）
#
# **通常不用手动起**：开发模式下 Electron 自己会拉起它 —— 
# `desktop/src/main/pg.ts` 在 spawn sidecar 之前确保 5432 可用
#（路径用 `PG_HOME` 覆盖，默认 `D:/pg`），退出时 `pg_ctl -m fast` 干净停止。
#
# 想先起好省等待（或 PG 装在其他地方）：
#     bash start-desktop-pg.sh      # 起 PG + 启动 Electron，退出时干净停止

# 2. 后端依赖 + 建表（只做一次）
cd sidecar
pip install -r requirements.txt
# 要跑测试套件就改装这个，它会连带装上面的全部（pytest / httpx 不进部署环境）：
#   pip install -r requirements-dev.txt
alembic upgrade head              # 读取 DATABASE_URL，无需改 alembic.ini

# 3. 学生端（会一并拉起 sidecar 与数据库）
cd desktop
npm install
npm run dev

# 教师端（浏览器访问，共用同一后端）
npm run dev:web
```

⚠️ **数据库没起来，症状不是「没有持久化」，而是「每一页都 Network Error」。**

这一条值得单独说，因为它和直觉相反，而且**日志里没有任何异常**：

| 环节 | 行为 |
| --- | --- |
| `GET /health` | 不碰数据库 → **200**，主进程据此判定引擎就绪并正常开窗 |
| 题库 / 错题本 / 教师端 | 连不上 5432 → **挂住**（不报错，连 uvicorn 访问日志都不打） |
| 前端 | 30 秒超时或连接被重置 → `Network Error` |

所以看到的现象是「引擎看起来是好的，但每一页都报错」。2026-09-20 实际发生过一次。
**排查第一步永远是 `netstat -ano \| findstr 5432`** —— 而不是去翻 sidecar 日志。

**第二种「每页 Network Error」，成因完全不同，2026-09-22 定位**：上一次关窗口时
dev server 没退干净，**5173 一直有人占着**。`electron-vite` 遇到端口被占**不报错**，
而是直接复用那个旧服务，然后把新起的 Electron 主进程交给一个它不适配的环境 ——
主进程在模块初始化阶段就崩了：

```
TypeError: Cannot read properties of undefined (reading 'isPackaged')
    at @electron-toolkit/utils/dist/index.cjs:6
```

于是**你看到的窗口是旧服务的（能正常渲染），而后端（sidecar）根本不存在** ——
现象和上面一模一样，日志却指向别处。这个坑的排查口诀：

- 崩在 `@electron-toolkit/utils` 且提到 `isPackaged` → **先看 5173 有没有人占**；
- `netstat -ano | findstr 5173`，比 `npm run dev` 的输出更能说明问题。

**已加防护**（`desktop/src/main/devserver.ts`，2026-09-22）：dev 模式启动时先探一次
5173，若被别的进程占着就杀掉它再启动（只认这一个端口、只杀占用它的那个进程、
绝不杀自己；认不出占用者时宁可不杀）。所以正常情况下不会再撞上，但**下面这条习惯
仍然值得保持**：重启前先在原终端 `Ctrl+C`，等它完全退出，别在窗口还开着时直接再启一次。

数据库状态本身可以用 `GET /api/v1/env-check` 看（它会真的去连库）。

**启动失败现在会说出来。** 后端拉不起来时，启动画面不再只写「分析引擎未就绪，
将继续启动…」——那句话真实但无用，既没原因也没下一步。现在会显示
**具体是哪个错误**（取 sidecar 自己的最后一行输出，Python 把原因放在 traceback
末尾），并停留约 5 秒供你截图（`desktop/src/main/index.ts` 的 `FAILURE_HOLD_MS`）。
排错时也可以直接贴这一行，不用再去翻终端。

另一个坑：**崩溃恢复很慢，而且会累积。** 硬杀 PostgreSQL 后它会 fsync 整个数据
目录才接受连接，实测 40 秒以上，**每硬杀一次就更慢**（每次都排一次全量 sync）。
期间 `pg_isready` 一直返回 "rejecting connections"。所以：

- 让应用自己起停（它用 `-m fast` 干净停止），不要手动强杀；
- 干净关闭后冷启动只要 **2 秒**；
- 万一真在恢复，启动画面会说「数据库恢复中…（已等待 N 秒）」，等着就行。

> **sidecar 不需要单独启动。** `npm run dev` 启动 Electron 后，
>   
> 主进程会用随机端口 + 随机 Token 拉起 sidecar，等 `/health` 通过再显示窗口，
>   
> 退出时连同 uvicorn 的子进程一起清理。sidecar 日志以前缀 `[sidecar]`
>   
> 混在 Electron 的终端输出里。

也可以直接用根目录的一键脚本：`start.bat` 或 `start.ps1`。


### 测试

```bash
cd sidecar

# 日常用这条：跳过 eval_set
env -u PYTHONPATH python -m pytest ../tests -q -m "not eval_set"

# 只在确实要测真实模型时跑：会调用付费端点、按测试计费、结果不可复现
env -u PYTHONPATH python -m pytest ../tests -q -m eval_set
```

三点说明，都是实测踩过的：

- **`env -u PYTHONPATH` 不能省。** 否则 `sitecustomize.py` 会让清理阶段的
    
  `Path.unlink` 抛 `SystemExit(1)`，表现为一大批与本次改动无关的失败。
- **默认不要跑全量。** `eval_set` 那批会真的请求 LLM 服务，既计费又不可复现——
    
  **不要把它当成「跑个全量」的顺手选项**。
- 慢的是**真实 C++ 编译**（单文件约 88 秒），不是 LLM。
- **进程创建开销可能退化到 5 秒以上**，那时一切真实执行都会 TLE。先用
    
  `python -c "import subprocess,time;t=time.perf_counter();subprocess.run(['whoami']);print(time.perf_counter()-t)"`
    
  量一下：正常是几十毫秒，2026-09-19 实测一度是 **5.2 秒**（`CreateProcess`
    
  被安全软件挂钩，与本仓库无关）。判题的上限是 5 秒，所以那时候**正确的代码
    
  也会判 TLE**——这是机器的问题，不是判题器的问题。断言「程序正确」的测试因此
    
  用 `conftest.EXEC_TIME_LIMIT`（30 秒）作为预算；「超时会被杀」由
    
  `test_timeout` / `test_judge_tle` 用 1 秒上限各自覆盖，不受影响。

写组件测试时的五个坑（都实测踩过）：

- ⚠️ **样式必须跟着标记一起搬进子组件。** 两个父组件都是 `<style scoped>`，而
    
  scoped 规则只作用到子组件的**根元素**，穿透不到内部的 `li` / `button` / `pre`。
    
  留在父组件里就是**静默失效**——构建不报、测试不报，只有眼睛能发现。这是本次
    
  抽取里唯一一个「不做就必然出错且不会报警」的点。
- **必须 `attachTo: document.body`。** 组件用 `v-show` 控制分层，断言要看
    
  **可见性**而不是元素存不存在；而 `isVisible()` 读 computed style，jsdom
    
  对**游离节点**算不出值，于是已释放的段落也会被判不可见——不挂上去，测试会
    
  「状态明明对了却失败」，且看不出错在哪。
- **环境要 opt-in。** 全局仍是 node（api 层测试不需要 DOM，套上白付开销），
    
  需要 DOM 的 spec 在文件首行写 `// @vitest-environment jsdom`。
    
  `vitest.config.ts` 里的 `vue()` 插件是另一处必需项：没有它，import `.vue`
    
  会被当成语法错误。
- ⚠️ **`vi.mock` 的工厂会被提升到所有 import 之前**，所以它**不能引用外层的
    
  `const`**（报 `Cannot access 'X' before initialization`）。三件事要一起记住：
    
  ① 替身状态放进 `vi.hoisted()`；② 那里拿不到 `ref` / `defineComponent`
    
  （`vi.hoisted` 的时机早于 import），要用就在工厂里 `await import('vue')`；
    
  ③ 别把可变状态挂在 mock 模块的额外导出上——那个名字真模块没有，取回来要
    
  过类型断言，等于给 `any` 开后门（`no-explicit-any` 在 CI 里是 error）。
- ⚠️ **`onMounted` 里赋的值，`mount()` 之后立刻读不到。** 首次渲染发生在
    
  mounted 之前，设置 ref 引发的重渲染是**异步**的——`RadarChart` 的调色板
    
  就是这样：不 `await nextTick()` 只会读到 `{}`，而且不会报错（`{}.radar`
    
  只是 `undefined`，要等断言才炸）。另外 `vi.mock('vue-echarts')` 之后断言的是
    
  **传进去的 option**，不是画出来的 canvas——canvas 在 jsdom 里画不出来，
    
  而画不出来并不等于 option 是对的。

### 数据库说明

`DATABASE_URL` 是生产 PostgreSQL DSN（`postgresql+asyncpg`）。
  
API 路由是同步的，`app/db.py` 会把 asyncpg URL 自动改写为
  
`psycopg` 同步驱动——所以**不会**再静默降级到 SQLite。
  
同步路由需要指向另一个 DSN 时，用 `DATABASE_URL_SYNC` 覆盖。
  
测试通过 monkeypatch `get_session` 使用 SQLite，无需真实 PG——**但这也意味着
  
SQLite 不会替你发现方言问题**（它默认不强制外键，函数名也不同）。

要跑真 PostgreSQL：

```bash
./tools/pg_verify.sh   # 起 PG → 迁移到 head → 跑聚合 SQL → 干净停止
```

需要 `D:\pg` 的 zip 版 PostgreSQL 17.6（免安装、无服务、无管理员）。脚本头部
  
写了三个必知的坑，其中最容易踩的是：**PG 不跨 shell 调用存活**，所以启动与
  
使用必须在同一次调用内完成——脚本就是那一次调用，别拆开手工跑。
