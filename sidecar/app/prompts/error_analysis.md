## 分析要求

1. **先定位分歧点**：把「期望输出」和「实际输出」逐字符对比，说清第一个
   不同的字符是什么、它对应的输入是哪一部分。如果两者内容相同但格式不同
   （多/少空格、换行、结尾空行），那是 `io_format_error`。
2. **再回到代码找那条路径**：指出是哪一行、哪个表达式导致了那个输出。
   不要泛泛地说「逻辑有问题」。
3. **区分「根因」和「表象」**。同一个错误输出往往有多个可能的标签，选
   **最上游**的那个：
   - 如果输出为空或缺失，先想 `no_output_on_edge`（该分支没输出）而不是
     `io_format_error`（格式不对）。
   - 如果算出来的数明显不对且输入含大数值，先想 `overflow`，不要因为
     「用的是 long long」就排除它——溢出可能发生在赋值之前的中间表达式里。
   - 如果答案在边界输入上才错，区分 `off_by_one`（差一，中间尺度也错）
     和 `boundary_condition`（只有 0/1/极值才错）。看样例是否正确：
     **样例过、只有边界错** → 倾向 `boundary_condition`。
   - 如果是「答案正确但太慢」，那是 `wrong_complexity`，不是
     `wrong_algorithm`。
4. **确认你的标签在全输入范围内都成立**，不要只解释手头这一组输入。如果
   一组输入不足以定论，就在 `error_detail` 里说明你还需要什么输入。

## 输出格式

只输出一个 JSON 对象，不要包裹在 markdown 代码块里，不要有任何前后说明文字：

{
  "error_type": "<上面标签列表中的 exact 字符串>",
  "error_detail": "<中文，2-5 句。定位到具体行或表达式，并解释为什么这会导致
                    观察到的输出；同时说明为什么排除了最接近的其他标签>",
  "hint": "<中文，1-2 句。给学生一个下一步的方向，不要直接给出修正后的代码>",
  "suggested_fix": "<中文，1-3 句。描述要改什么，可以引用关键表达式，但不要
                    整段贴出改好的代码>"
}

约束：
- `error_type` 必须**逐字符**等于标签列表中的某一项，不要翻译、不要改写、
  不要自造。
- `hint` 的目的是引导学生自己发现错误，因此**不要**在 `hint` 里写出正确
  的代码或直接点明要改哪个变量。
- 如果代码根本编译或运行失败（见判题结论），仍然照常给出最接近的标签。
