# AlgoForge 欠缺清单

> 核查时间：2026-09-16。每条都标了**证据**（文件/行号），可以自己去看。
> 按「会不会当场翻车」排序，不是按工作量。

---

## 一、会让演示当场翻车的（3 条）

### 1.1 点「提交」会卡住等 AI，最长 5 分钟 ⚠️ 最严重

**证据**：`sidecar/app/api/judge.py:182` 是 `await asyncio.to_thread(_judge_and_record)`，
而 `_judge_and_record` 里面 `sidecar/app/records.py:295` **同步**调用了 `analyze_error`。
`.env` 里 `LLM_TIMEOUT=300`。

**后果**：判题其实几毫秒就跑完了，但 HTTP 响应要一直等到 LLM 分析回来才发出去。
学生点完提交，界面就冻在那里，最长 5 分钟，中间没有任何反馈。
（WebSocket 的 `judge_done` 按设计要等落库 commit 才发，所以那段时间也是静默的。）

**怎么补**：判题和落库先返回，分析改成后台任务；
前端给错题本条目一个「分析中」状态，分析完再刷新。这一步和 S8 的流式是同一件事的两半。

---

### 1.2 分析失败是静默的，而且没法重试

**证据**：`records.py:304-312`——`analyze_error` 失败只写一行日志然后 `return`，
条目永远停在"未分析"。全项目搜索 `analyze_error` 的调用点，**只有 `records.py:287` 这一处**。

**后果**：一次网络抖动或超时，这道题的错因就永久丢失，学生和老师都不知道为什么没有分析结果。
没有「重新分析」的按钮，也没有任何补跑机制。

**怎么补**：错题本条目加 `analysis_status` 字段（pending / done / failed），
再开一个 `POST /mistakes/{id}/analyze` 让前端能重试。

---

### 1.3 前端根本看不到诊断结果（练习页）

**证据**：`desktop/src/renderer/src/api/` 下 9 个文件，**没有一个是 agent / analyze 的**；
`error_type`、`agent_suggestion` 这些字段只在 `MistakesView.vue` 里出现。

**后果**：README 写的主线是「运行 → 判题 → **诊断** → 追踪 → 调度」，
但在练习页做完题，学生看不到诊断，得切到错题本页去找。
整条闭环在 UI 上是断的——这是毕设演示最容易被问住的地方。

**怎么补**：练习页在判题结果下面加一块诊断区，订阅该提交的分析结果。

## 二、README 写了但代码里没有的（4 条）

这类问题不致命，但**答辩时被翻出来会很尴尬**，而且说明文档在自我欺骗。

| README / AGENTS.md 说 | 实际情况 | 证据 |
|---|---|---|
| `stores/` — Pinia 状态管理 | **完全没有 Pinia** | 全项目 grep `pinia` → 0 命中；`src/renderer/src/` 下无 `stores/` 目录 |
| `components/HintCard` | 不存在 | `find src -iname "*hint*"` → 空 |
| `composables/useRunStream`、`useLLMStream` | 不存在（只有 `usePageCrumb`、`useSidecarStatus`） | `ls src/renderer/src/composables` |

**怎么补**：要么补上，要么**改文档**。我的建议是——Pinia 和那两个 composable
如果现在用不上（状态直接用 ref 就够了），就**把 README 改掉**，别写没做的东西。
但 Vitest 建议真补：`RadarChart`、`VerdictBadge`、SM-2 排期这类纯逻辑组件，
测试成本很低，却能在答辩时说"前后端都有测试"。

## 三、工程基础设施缺的（3 条）

### 3.1 没有 CI

**证据**：仓库根目录没有 `.github/`。

**后果**：570 个测试只在"记得跑的时候"跑。改一次 taxonomy 忘了跑评估集，
或者前端类型检查挂了，都没人拦。

**怎么补**：一个 `pytest -m "not eval_set"` + `ruff` + `vue-tsc` 的 workflow 就够了，
不需要复杂。注意 `eval_set` 那批要跳过（依赖真实 LLM）。

### 3.2 没有 LICENSE 文件

**证据**：根目录无 `LICENSE`，但 `README.md` 第 239 行写了 `MIT`。

**后果**：法律上等于"未声明授权"，别人不能合法使用。开源项目这是硬性缺失。

**怎么补**：加一个 MIT LICENSE 文件，30 秒的事。

### 3.3 `sidecar.log` 提交进了仓库

**证据**：仓库根目录有 `sidecar.log`。

**怎么补**：确认 `.gitignore` 覆盖它，然后从版本控制里移除。

## 五、只有你自己能解决的两件事（外部视角看不到）

### 5.1 界面从来没被人真正看过

本机没有 PostgreSQL，所以四个业务页（练习/错题本/画像/复习）**只显示连接错误态**。
PU-6 到 PU-10 的响应式布局、交互、主题，全部**只在构建产物层面验证过，没有真人目视**。

**风险**：这是毕设演示的核心。第一次在答辩现场看到真实界面，就是最危险的时刻。

**怎么补**：装个 PostgreSQL（Docker 一行命令），或者临时让 sidecar 指向 SQLite，
把四个页面**自己点一遍**。这一步没有任何技术含量，但价值最高。

### 5.2 数据库迁移只在 SQLite 上验过

`AGENTS.md` 硬性要求 PostgreSQL，但 PU-11 / PU-13 的迁移**只在本机 SQLite 上验证过**。
SQLite 用 `batch_alter_table` 能过，不代表 PG 上能过。

**怎么补**：同上，起一个 PG 跑一次 `alembic upgrade head`。

## 六、S2 那 50% 到底该怎么看（用大白话重说一遍）

之前那份文档写得太绕，这里重说：

- 你的评估集有 **20 道题**，所以**每道题值 5 分**。
- 门槛是 60%，也就是要答对 **12 道**；实测答对 **10 道**。
- 差别就是 **2 道题**。

**问题在于**：20 道题的样本太小，答对 10 道和 12 道之间的差别，
跟"运气好坏"的差别差不多大。所以：

> **不能说"50% 没达标"，只能说"用这 20 道题测不出它到底达没达标"。**

这不是在说你的模型没问题，而是在说**现在的尺子不够精确**。

**最省事的三步**：
1. 先让报告把"不确定范围"也打出来（比如 `50%（大约 30%~70%）`），
   这样你一眼就知道该谨慎到什么程度。改十几行。
2. **按标签看，而不是只看总分**。总分 50% 没用，但"哪些标签错得多"有用。
   大概率是几对容易混的标签在互相错（比如 `overflow` 和 `wrong_data_type`），
   这直接告诉你 prompt 里哪条消歧规则没生效。
3. 补题：先让 12 个标签**每个至少 3 道题**（共 36 道），
   这样单题权重从 5 分降到 2.8 分，尺子就细多了。

**最不建议做的**：把同样的 20 道题重跑 5 次然后说"样本变大了"。
那还是 20 道题，只是同一个东西测了 5 遍——尺子一点没变细。

## 七、总结：这个项目其实不差

把上面全看完，值得先说清楚的优点：

- **31 个后端测试文件，基线 570 passed** —— 同类项目里（PrepDojo 31★、Recall 2★）
  有测试的极少，有**带金标签的评估集**的一个都没有。
- **0 个 TODO / FIXME** —— 代码是真的写完了，不是堆着半成品。
- **taxonomy 设计成熟** —— 12 个标签按阶段分组，还主动删过"表象型"标签
  （`no_output_on_edge`），这是有方法论的表现。
- **错因受控词表 + 严格 schema 校验** —— 比绝大多数同类项目严谨。

**真正要命的只有第一章那 3 条**（阻塞、无重试、前端看不到）。
它们都不是"能力不够"，而是**接线没接完**——能力都在，就是没接到用户面前。
按 1.1 → 1.2 → 1.3 的顺序修，一天之内能改完。
