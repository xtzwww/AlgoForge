## 0. 先说清 `sevan017/leetcode_awsome` 是什么

它**不是系统，是个人刷题归档**。事实：

| 项                   | 值                                                                                               |
| ------------------- | ----------------------------------------------------------------------------------------------- |
| star / fork / issue | **0 / 0 / 0**                                                                                   |
| 创建 / 最后推送           | 2026-04-22 / 2026-09-16（今天还在推）                                                                  |
| 语言                  | Java                                                                                            |
| 仓库体积                | 333 KB                                                                                          |
| 根目录                 | 只有 `.gitignore`、`README.md`、`src/` 三样                                                           |
| 文件构成                | **124 个条目**，全是 `.java`，按日期分目录                                                                   |
| 目录分类                | `daily_question/_2026/_0426…`、`hot100`、`huawei_od`、`luogu`、`newcoder`、`mock_interview`、`左成云新手班` |
| 构建配置                | **没有**（无 `pom.xml`、无 `build.gradle`）                                                            |
| LICENSE 文件          | **没有**（但 README 里写了「本项目采用 MIT 许可协议」）                                                            |

**它的 README 在描述一个不存在的产品**：题库练习、解题代码、算法分析、代码优化、社区交流。  
而「使用方法」一节写的是「（此处可以添加项目安装、配置和使用方法的说明）」，  
「贡献指南」写的是「（此处可以添加如何参与项目开发的说明）」——**占位符没删**。

所以：**它和 AlgoForge 不在同一层**。拿它当竞品对比是不成立的  
（这正是我第一份调研里说的"圈层混淆"）。  
但它作&#x4E3A;**"反面教材标本"**&#x5F88;有价值——它一次性演示了 4 种最常见的缺陷。

**另外一个实际用途**：这 124 道题解（含 hot100、华为 OD、洛谷、牛客）  
是你 `corpus/` 可以用的语料，比从 labuladong 搬运更贴你的目标场景。  
（注意：仓库无 LICENSE，法律上默认保留所有权利，用之前得问作者要授权。）

## 2. 六种典型缺陷，逐个对照

### 缺陷 A：README 画大饼（承诺 ≠ 实现）

| 项目                  | 表现                                                                                                     |
| ------------------- | ------------------------------------------------------------------------------------------------------ |
| `leetcode_awsome`   | **最严重**。README 描述"平台 + 社区"，实际是 .java 归档，占位符都没删                                                         |
| **AlgoForge**       | **中等**。README 列了 `stores/`(Pinia)、`components/HintCard`、`composables/useRunStream`、前端 Vitest —— 四个都不存在 |
| PrepDojo / LeetLens | 基本准确                                                                                                   |

**为什么这是"缺陷"而不是"小问题"**：README 是别人（老师、面试官）判断你的**唯一入口**。  
README 承诺 10 分、实际 6 分，比 README 承诺 6 分、实际 6 分**更差**——  
因为前者让人觉得你在虚报，后者让人觉得你诚实且做到位了。

**修法**：把 README 里没做的东西**删掉**（不是补上）。Pinia 和那两个 composable  
如果现在用不上，就别写。这是半小时的活，但答辩印象分差别很大。

---

### 缺陷 B：声称 MIT 但没有 LICENSE 文件

| 项目                | 表现                                  |
| ----------------- | ----------------------------------- |
| `leetcode_awsome` | README 写 MIT，根目录无 LICENSE           |
| `Ankicode`        | README 写 "License MIT"，根目录无 LICENSE |
| `code-aid`        | 无 LICENSE 也无声明                      |
| **AlgoForge**     | README 第 239 行写 MIT，根目录无 LICENSE    |

**3/8 的项目犯这个错。** 法律上"没有 LICENSE 文件"= 默认保留所有权利，  
别人**不能合法使用你的代码**。写 MIT 是没用的，必须放文件。

**修法**：根目录加一个 `LICENSE`（MIT 全文 + 你的名字 + 2026）。**30 秒。**

| 项目                                                                                       | 表现           |

| **AlgoForge**                                                                            | 无 `.github/` |

**5/8 没有 CI，所以这是通病。** 但对你的伤害比对别人大，因为：

  没有 CI 就没人拦；

**修法**：见下面 §3.1，PrepDojo 的 CI 可以直接改造成你的。

### 缺陷 E：依赖不锁版本 / runtime 与 dev 依赖不分

**AlgoForge 现状**（`sidecar/requirements.txt`）：

```
fastapi>=0.115.0
pytest>=8.0.0        ← 测试依赖混在运行依赖里
httpx>=0.27.0        ← 同上
pyyaml>=6.0
psutil>=5.9.0
...
```

两个问题：

1. **`pytest` 和 `httpx` 是测试依赖，却写在 `requirements.txt` 里** ——  
   部署时会把测试框架装到生产环境。PrepDojo 用 `requirements-dev.txt` 分开。
2. **全是 `>=` 下界，没有上界也没有 lockfile** —— 依赖升级随时可能静默破坏构建。  
   （这个坑你在 P2-5 已经踩过一次同类的：`LLM_MAX_TOKENS`/`LLM_TIMEOUT` 的默认值  
   伪装成"模型答错"。）

**PrepDojo 的做法**：单独 `requirements-dev.txt`，并且 CI 里锁 `pip==26.2.1`

- `pip check` + `pip-audit`。

**修法**：拆 `requirements-dev.txt`（5 分钟）；上界和 lockfile 可以延后，  
但拆分现在就该做，否则写 CI 时还得再改一次。

## 3. 反过来：同类做对了、而你还没做的（3 条）

### 3.1 PrepDojo 的 CI —— 可以直接抄结构

它有 **5 个作业**，全部 `timeout-minutes` 限时，action 用 **commit SHA 锁版本**（供应链安全）：

| 作业                 | 干什么                                                                                                                             |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------- |
| `test`             | Python **3.10 / 3.12 / 3.13 三版本矩阵**，`fail-fast: false`；`pip install -r requirements-dev.txt` → `pip check` → `pytest tests/ -q` |
| `macos-local`      | macOS 上装 Node 22 跑一遍，验证本地模式                                                                                                     |
| `frontend-syntax`  | `node --check app.js`（没有前端框架，所以只查语法）                                                                                            |
| `docker-judge`     | 构建判题镜像 + 只跑 `test_judge_docker.py`                                                                                              |
| `dependency-audit` | `pypa/gh-action-pip-audit` 查依赖漏洞                                                                                                |

**给你的最小可用版本**（3 个作业就够）：

```yaml
name: CI
on: [push, pull_request]
permissions: { contents: read }
jobs:
  backend:
    runs-on: ubuntu-latest
    timeout-minutes: 15
    steps:
      - uses: actions/checkout@<SHA>          # 照 PrepDojo 锁 SHA
      - uses: actions/setup-python@<SHA>
        with: { python-version: "3.12", cache: pip }
      - run: pip install -r sidecar/requirements.txt -r sidecar/requirements-dev.txt
      - run: python -m ruff check .
      - run: python -m pytest tests -q -m "not eval_set"   # eval_set 要真实 LLM，必须跳过
  frontend:
    runs-on: ubuntu-latest
    timeout-minutes: 10
    steps:
      - uses: actions/checkout@<SHA>
      - uses: actions/setup-node@<SHA>
        with: { node-version: "22", cache: npm, cache-dependency-path: desktop/package-lock.json }
      - run: npm ci && npm run typecheck    # 或 npx vue-tsc --noEmit
```

**关键一条**：`-m "not eval_set"` 必须带上——你的评估集要调真实 LLM，  
放 CI 里会既慢又烧钱还不稳定。（你自己在 README 里也是这么写本地跑法的。）

## 4. 结论：哪些是"通病"（不用慌），哪些是"只有你缺"

### 通病（同类普遍都有，改起来快，不影响你相对别人强）

| 缺陷           | 同类发生率      | 修的成本     |
| ------------ | ---------- | -------- |
| 无 LICENSE 文件 | 3/8        | 30 秒     |
| 无 CI         | 5/8        | 1 小时     |
| README 与实际不符 | 2/8 明显（含你） | 半小时（删内容） |
| 依赖不锁版本       | 普遍         | 5 分钟（拆分） |

### 只有你缺的（这些才是真问题）

| 缺陷                   | 同类情况                    | 为什么只有你要紧                           |
| -------------------- | ----------------------- | ---------------------------------- |
| **提交阻塞等 AI 最长 5 分钟** | 同类都是异步或后台               | 这是你独有的架构问题（`judge.py:182` 同步等 LLM） |
| **分析失败静默 + 不可重试**    | 同类都有重试入口                | 你的调用点只有一处，错了就永久丢                   |
| **前端看不到诊断结果**        | LeetLens/Recall 都在做题页展示 | 你的闭环在 UI 上是断的                      |
| **前端 0 测试但文档说有**     | —                       | 文档撒谎比没测试更糟                         |
| **界面从没被人真正看过**       | —                       | 只有你本机没有 PG，别人能跑起来                  |

**一句话**：你的"欠缺"分成两类——**门面类**（LICENSE/CI/README）是通病，  
一天能全修完；**架构类**（阻塞/重试/前端看不到）只有你有，因为只有你真做到了  
"AI 分析接进判题流程"这一步——**同类项目大多还没走到那一步，所以还没遇到这个问题**。

这算是个"幸福的烦恼"。

## 5. 建议的动手顺序

1. `LICENSE` + 删 README 里不存在的组件 + 拆 `requirements-dev.txt` —— **1 小时，纯体力活**
2. 加 CI（3 个作业）—— **1 小时**
3. 修"分析失败静默 + 不可重试"（加 `analysis_status` + 重试接口）—— **半天，价值最高**
4. 练习页接诊断结果 —— **半天**
5. 把提交改异步 —— **1 天，改动最大，但演示体验差别最大**
6. 装 PG，把四个页面自己点一遍 —— **1 小时，价值密度最高**

**第 1、2、6 步加起来不到 3 小时，能解决"门面"和"从没人看过界面"两个大问题。**  
如果时间紧，先做这三步。
