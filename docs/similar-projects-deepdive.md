## 1. 沙箱工具循环的工程规范 → S3

来源：`PrepDojo/prepdojo/chat.py`（全文已读）。

### 1.1 三重预算，缺一不可

```python
MAX_TOOL_ROUNDS = 8          # LLM↔工具 往返轮数
MAX_TOOL_CALLS = 3           # 单轮对话内工具调用总数
CHAT_TOTAL_TIMEOUT = 180.0   # wall-clock 总时限
```

**为什么三个都要**：`MAX_TOOL_CALLS` 防单轮爆炸，`MAX_TOOL_ROUNDS` 防多轮打转，
`CHAT_TOTAL_TIMEOUT` 防慢工具把整轮拖死。只设一个都会留下一种死法。
AlgoForge 的 S3 目前只有超时概念，需要补上前两个。

### 1.2 反幻觉的核心：让"事实"由工具独占

这是整个设计里最值得抄的一条。它的 system prompt 写：

> 1. 沙箱与测试用例的结果是唯一事实；你的判断与它冲突时以它为准。
> 2. 不直接给完整答案代码，除非考生明确说"我要看答案"——引导为主。

并且**在 JSON schema 里把判定字段锁死来源**：

```json
{
 "sandbox_verdict": "从工具结果读到的判定（AC/WA/TLE/MLE/RE/CE，必须与沙箱一致）",
 ...
}
```
> 注意：sandbox_verdict 只能来自工具返回的事实；分析结论与工具结果冲突时，以工具为准并修正你的分析。

**这条模式可以直接迁移到错因分析**：AlgoForge 现在把 `verdict` 作为文本变量注入 prompt，
模型是"读到"判定而不是"查到"判定。S3 之后应该要求模型**先调判题工具**，
再让 `error_type` 的推理链建立在工具返回的判定与逐用例结果上。
这能直接压掉一类错误：模型基于"代码看起来对"而假设判定是 WA。

### 1.3 工具返回的体积预算（直接照抄的数值）

| 字段 | 上限 | 理由 |
|---|---|---|
| `stdout` | 4000 字符 | 输出可能极长，会吃掉上下文 |
| `stderr` | 1500 字符 | 编译错误栈通常够用 |
| `compile_error` | 2000 字符 | 同上 |
| 注入的考生代码 | 12000 字符 | 与题面分开计 |
| 题面 | 20000 字符 | — |

**附带一条诚实提示**：`run_code` 的返回里带
`"note": "RE/TLE/MLE 时 stdout 可能不完整"`——
它明确告诉模型"这个字段可能不可信"，而不是让模型自己猜。

### 1.4 隐藏用例只回判定，不回内容

```python
payload = {
    "verdict": res.verdict,
    "max_time_ms": res.max_time_ms,
    "cases": [{"idx": c.idx, "verdict": c.verdict, "time_ms": c.time_ms} for c in res.cases],
}
```
工具描述里明写「隐藏用例内容不会返回」。

AlgoForge 的隐藏用例设计（`is_sample` 不拦截，靠路由走哪条 SQL）与之一致。
**这里的增量是**：即使模型主动调判题工具，也只能拿到 `verdict`，拿不到隐藏用例的
`input/expected`。这是"让 Agent 自主调工具"和"不泄漏隐藏用例"两个目标能同时成立的
**唯一可行做法**——否则 S3 一开工具，隐藏用例就自动泄漏了。

### 1.5 循环的优雅终止

超预算时不抛异常，而是**注入一条合成的 user 消息把模型逼出结论**：

```python
if tool_calls_used >= MAX_TOOL_CALLS:
    messages.append({"role": "user",
        "content": "（工具调用总数已达上限，请基于已有沙箱事实直接给出结论。）"})
```
单个工具调用超限时，回一条 tool 消息而非异常：
```python
{"error": f"本轮工具调用总数上限为 {MAX_TOOL_CALLS}，请直接作答"}
```

**AlgoForge 的对照**：P2-3 的重试机制处理的是"输出不合 schema"，
但没有处理"Agent 不肯收手"。S6（ReAct 自检循环）必然遇到这个问题，
这套"合成消息收尾"的做法比抛异常好——抛异常等于丢失已经花掉的 token。

### 1.6 一个容易被忽略的产品细节

它的教练 system prompt 第 0 条：

> **先回答考生问的问题**……编辑器里的代码只是背景信息；
> **考生没有问代码时，不要主动发起对它的编译/运行分析**，
> 只有问题确实涉及他的代码（debug、点评、判题验证）时才调用工具。

这是**成本控制**也是**体验控制**：Agent 有工具就爱用工具。AlgoForge 到 S3 会有同样的问题。

## 2. 提示分级：把 `hint` 从单条变成可升级 → S2/S10

来源：`algo-sensei/modes/hint-mode.md`（全文已读）。

它把提示做成**固定的 5 级梯度**，并且有一条硬规则：

> **NEVER:** Jump straight to code / Give the complete solution / **Skip levels (always progressive)**

| 级别 | 给什么 | 不给什么 |
|---|---|---|
| L1 观察 | "输入结构有什么特点？""最简单的情况呢？" | 任何方向 |
| L2 模式识别 | "这让你想起哪类经典题？" | 具体技巧名 |
| L3 方向 | "如果记录下你见过的东西呢？" | 技巧名 |
| L4 具体技巧 | "这是双指针/DP 问题" | 代码 |
| L5 伪代码骨架 | 带注释的骨架 | 完整代码 |

**对 AlgoForge 的意义**：现在 schema 里 `hint` 是单条自由文本，
学生看完就没了——要么懂了，要么还得问一次（重新走一遍完整分析，浪费一次调用）。

建议改动（两处，都不大）：
1. `ErrorAnalysisResult` 增加 `hint_level: int`（1-5）与 `next_hint_hint`（下一级提示的触发条件）；
2. 前端 `HintCard` 增加"再来一个提示"，**只带上下文重调 hint 字段**，不重跑整个分析。

另外 algo-sensei 按题型给了不同的梯度序列（数组/树/DP/图/贪心各一套）。
AlgoForge 的 `corpus/problems` 已有题型信息，可以把这层映射做进 prompt 模板。

**要警惕的一点**：algo-sensei 是纯 prompt 包，没有 schema 校验，
它的 "NEVER give the complete solution" 全靠模型自觉。
AlgoForge 有 schema 层，应该把它变成**可校验的约束**（见 §6）。

## 3. 知识锚点：让 AI 输出知识点 → 自举 RAG 语料 → S5

PrepDojo 的 AI 判题报告 JSON 里有这两个字段：

```json
"better_solution": {"exists": true, "name": "哈希表", "complexity": "O(n)", "hint": "思路提示（不给完整代码）"},
"related_knowledge": ["更优解法背后的知识点讲解，1-3 条，每条一个知识点：原理/trade-off/典型场景"]
```

它的 system prompt 解释了这个设计的意图：

> **多解法对比与知识延伸**：……把每道题变成一个**知识锚点**。

**这对 AlgoForge 有两层价值**：

1. **画像层的输入**。AlgoForge 的知识点统计目前来自题目的 `knowledge_tags`
   （人工标注、静态）。如果 Agent 每次分析都输出它认定的知识点，
   画像就能从"题目维度的标签"升级为"Agent 认定的薄弱点维度"——两者不一致本身就是信号
   （题目标了"动态规划"，但 Agent 认为学生的错误发生在"边界处理"上）。

2. **RAG 语料的自举**。`corpus/knowledge_cards/` 现在是空的，
   S5 需要语料。让 Agent 在分析时顺带产出结构化的知识点解释，
   跑一段时间后就是一批**真实错因驱动**的语料——比从 `labuladong/fucking-algorithm`
   直接搬运更有针对性，也绕开了第三方内容的版权问题。

**注意边界**：PrepDojo 的 `related_knowledge` 是每题的临时产物，没有沉淀。
AlgoForge 要做的增量是**落库 + 去重 + 人工抽检**，否则会积累大量重复卡片。

## 4. CodeAid 的 D1–D4：D4 是 AlgoForge 的缺口

来源：CodeAid（CHI 2024，arXiv 2401.11314）。700 名学生、12 周部署、
8000 次使用记录的主题分析 + 每周问卷 + 22 场学生访谈 + 8 位教师访谈。

它给出的四条设计原则：

| 编号 | 原则 | AlgoForge 现状 |
|---|---|---|
| D1 | 发挥 AI 的独特优势 | ✅ 错因分析正是"人做不到大规模做的" |
| D2 | 简化提问形式，同时促进认知投入 | ⚠️ AlgoForge 是"提交即分析"，无需提问，简化到位但认知投入待验证 |
| D3 | **不给直接答案，鼓励有动机的学习** | ✅ prompt 与 schema 都守住了（`hint` ≠ `suggested_fix`） |
| D4 | **保持透明，让学生能评估并引导 AI 的回答** | ❌ **缺口** |

**D4 值得认真对待**。CodeAid 的原话是 "maintaining transparency and control for
students to asses and steer AI responses"——两个动词：**评估**与**引导**。

- **评估**：学生要能看到 AI 为什么这么判断。AlgoForge 的 `error_detail` 里确实要求
  "说明为什么排除了最接近的其他标签"，这是好的起点，但它埋在文本里，
  前端没有做成可视化的"证据链"。S8 的流式渲染解决的是"看到思考过程"，
  不是"看到判断依据"。
- **引导**：学生能否说"不对，我是知道边界的，问题在别处"？
  AlgoForge 目前没有这个入口——错因一旦入库就是既成事实，
  只影响 `agent_error_type`，学生无法反驳。

**这是个真实的产品缺口，也是毕设可以写进"未来工作"的差异点**：
加一个"我觉得不是这个原因"的反馈入口，把学生的纠正落库。
副产品是——**这批纠正就是最好的标注数据**，能反过来扩评估集（见 §5.4）。

## 5. 🔴 评估方法学：n=20 / 12 标签的硬伤

### 5.1 现状

`corpus/eval_cases/` 20 道题，`ROOT_CAUSE_LABELS` 12 个标签。分布：

| 标签 | 用例数 |
|---|---|
| `off_by_one` | 3 |
| `boundary_condition` / `io_format_error` / `missing_case` / `uninitialized_state` / `wrong_algorithm` / `wrong_data_type` | 各 2 |
| `inverted_condition` / `misread_problem` / `overflow` / `wrong_complexity` / `wrong_traversal` | **各 1** |

覆盖是完整的（12/12 都有用例），这比大多数同类项目都好。
**问题不在覆盖，在分辨率。**

### 5.2 硬伤：这个门槛分不出 50% 和 60%

每道题值 **5 个百分点**。S2 的门槛是 12/20 = 60%，当前 Ollama 实测 10/20 = 50%。

Wilson 95% 置信区间：

| 观测 | 点估计 | 95% CI | 区间宽度 |
|---|---|---|---|
| 12/20 | 60% | **[39%, 78%]** | 39pp |
| 10/20 | 50% | **[30%, 70%]** | 40pp |

**两个区间几乎完全重叠。** 换句话说：

> 以 n=20 的评估集，"50%" 和 "60%" 在统计上是同一个结果。
> 拿这个数字去触发「换模型 / 加 RAG / 调 prompt / 降标准」的 go/no-go 决策，
> **决策依据不成立**。

这不是在说 50% 没问题，而是在说：**现在无法知道它是不是问题。**

### 5.3 附带问题：5 个标签只有 1 个样本

`inverted_condition` / `misread_problem` / `overflow` / `wrong_complexity` / `wrong_traversal`
各只有 1 道题。模型在这 5 个标签上的表现，本质上**没有被测量**——
答错一个就是 -5pp，与随机噪声无法区分。

而 `overflow` 恰好是 prompt 里花了最多笔墨去和 `wrong_data_type` 做区分的那一对。

### 5.4 四条可执行的补救（按性价比排序）

**① 报告置信区间，而不是点估计**（成本：改十几行）

`AccuracyReport` 已经有 `describe()`。加上 Wilson CI 与"与门槛的距离"即可。
一行 `60% (95% CI 39–78%)` 会让所有读数字的人立刻知道该谨慎到什么程度。
**这是最便宜的一步，应该先做。**

**② 区分两种不确定性，分别处理**（成本：零，但要写清）

- **模型随机性**：`DEFAULT_TEMPERATURE = 0.0` 已经把这一项压到很低。
  注意托管端点在 T=0 下**也不是完全确定**（批处理与量化会带来差异），
  所以"重跑同 20 题取平均"只能收掉这一小部分，**解决不了主问题**。
- **用例代表性**：主导项。只有增加/替换用例才能改善。
  **不要把"重跑 5 次"当成"扩大了样本"**——那是 100 次观测 20 个样本，
  置信区间按 20 算，不按 100 算。

**③ 提高门槛的统计功效：n ≈ 150**（成本：高，但可以分阶段）

要在 80% 功效、单侧 α=0.05 下区分 p=0.6 与 p=0.5，需要约 **151 道题**。
一次性做不现实，可行的做法是：

- 把门槛改成**分层判定**：先要求"12 个标签每个至少 3 道题"（即 ≥36 道），
  此时单题权重降到 2.8pp，CI 宽度约 ±16pp——仍不够，但明显好转；
- 配合 ① 的 CI 一起用，把 gate 从"≥60%"改成"**CI 下界 ≥ 50%**"之类的稳健判据。

**④ 增加一个高分辨率指标：混淆矩阵**（成本：低，价值最高）

20 个样本算总体准确率分辨率不够，但**算混淆矩阵足够**——
因为模型的错误几乎不会是均匀分布的，而是集中在少数几对易混标签上
（`off_by_one` ↔ `boundary_condition`、`overflow` ↔ `wrong_data_type`、
`missing_case` ↔ `boundary_condition`——正是 prompt 里花最多笔墨区分的那几对）。

混淆矩阵能直接告诉你：**是哪一条消歧规则没生效**。
这比"总体 50%"有用得多——它把一个不可行动的数字变成了一个可行动的诊断。
`tools/s2_report.py` 已经在逐例打印，加上按标签聚合并输出 12×12 矩阵是自然的下一步。

### 5.5 外部对照：同类项目是怎么评估的

- **algo-sensei**（274★）：无评估，Roadmap 里进度追踪还没做。
- **PrepDojo**（31★）：有 pytest（判题五态、抽取、持久化、Web API），
  但**没有 AI 分析准确率的评估**。
- **Recall**（2★）：有 QA 验收清单，是功能验收不是质量评估。
- **CodeAid**（CHI 2024）：8000 次使用的主题分析 + 问卷 + 访谈——**定性为主、大样本**，
  没有用一个 20 题的门槛数字。

**结论**：AlgoForge 的 `eval_cases` + `AccuracyReport` + `s2_report.py`
在同类项目里已经是**领先**的（没有第二个开源项目建立了带金标签的错因评估集）。
但正因为它领先，它的方法学问题没有前人可以对照——
**CodeAid 的做法提示了一条替代路径**：当样本量撑不起定量门槛时，
用定性的错误模式分析（哪些消歧规则失效、失败案例的共同特征）替代硬数字，
把定量门槛留给样本量够大的阶段。

## 6. 顺手能修的两处小护栏

### 6.1 `hint` 泄漏检查可以更严

`schemas.py::_hint_must_not_leak_the_fix` 目前只拒绝 `hint == suggested_fix`（完全重复）。
但泄漏的常见形态不是完全重复，而是：

- `hint` 里直接贴了代码块（```）
- `hint` 里出现了 `suggested_fix` 中的关键表达式

这两条都是**纯字符串判断就能抓到的**，不需要额外 LLM 调用
（代码里已经明确说"语义比较超出范围"，这个边界是对的，但上面两条不是语义比较）：

```python
if "```" in self.hint:                       # 提示里不该有代码块
    raise ValueError("hint must not contain a code block")
```
第二条可以取 `suggested_fix` 里长度 ≥4 的标识符/表达式做交集，命中即拒。
**这是零成本的护栏加强**，而且与 D3（不给答案）直接相关。

### 6.2 工具调用上限的"预算"应该进配置

PrepDojo 把 `MAX_TOOL_CALLS` 写成常量。AlgoForge 刚在 P2-5 学到一课：
`LLM_MAX_TOKENS` 和 `LLM_TIMEOUT` 属于**模型属性**，应该进配置而不是硬编码
（memory: "调用方策略常量被写死在错误的层"）。
工具调用上限同理——**一次分析该调几次工具，取决于模型多爱调工具**，
不是代码常量。建议一开始就放 `settings.llm_max_tool_calls`。

## 7. 这一轮的方法论备注

- 上一轮的教训是"别用 awesome 关键词搜系统"；这一轮的教训是
  **"找到同类项目之后，真正有价值的信息在它的源码和它的评估方法里，不在 description 里"**。
  `PrepDojo/chat.py` 一个文件给出的可抄内容，比 30 个仓库的 description 加起来都多。
- 学术文献的可达性是个现实约束：Springer 章节重定向到付费墙，
  arXiv 摘要页信息量有限，**arXiv 的 HTML 版（`/html/{id}v2`）才是能拿到方法细节的地方**。
